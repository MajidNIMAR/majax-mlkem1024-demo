# Maintenance policy

This policy describes how the public project is kept reviewable over time. The
targets below express project practice and are not contractual service levels.

## Branches

`main` preserves the stable single-engine demonstrator. `development` contains
the expanded library and the ordered engineering work. Changes reach `main`
only through a deliberate stabilization decision. Development work must never
silently rewrite stable history.

Only the latest stable release and the current development revision receive new
corrections. Historical revisions remain available for traceability.

## Versioning

Release tags follow semantic versioning. Before version 1.0, a minor version may
change the public API. Patch versions preserve the public API and correct defects
or documentation. An incompatible cryptographic encoding or protocol contract
always requires a clearly identified compatibility break.

Every release requires a changelog entry, a clean verification run, reproducible
binaries, checksums, SBOMs, signatures and provenance generated by the release
workflow. The exact checklist appears in `docs/maintenance/release-checklist.md`.

## Dependency review

Dependencies remain exact in Cargo manifests and lockfiles. Dependabot opens
reviewable updates for Rust, GitHub Actions and Docker. Automated proposals do
not merge themselves. A cryptographic dependency update requires conformance,
negative, integration, assurance and performance evidence before acceptance.

Abandoned, unmaintained or unexpectedly expanding dependencies are candidates
for removal. The smallest dependency graph that supports the documented
behavior is preferred.

## Issue handling

New reports are classified as security, defect, compatibility, performance,
documentation or proposal. Reproducible failures and security impact take
priority over feature growth. Reports lacking enough information may remain
open while evidence is requested.

There is no guaranteed response time. The project aims to acknowledge private
security reports before routine issues and to publish status when a correction
requires extended investigation.

## Transparency

Public behavior changes appear in `CHANGELOG.md`. Completed engineering stages
retain their decision notes under `docs/development/`. Known claim boundaries
remain visible in `SECURITY.md`, `ADOPTERS.md` and the relevant evidence notes.
No benchmark, adoption, audit or conformance claim is published without a link
to the evidence supporting it.
